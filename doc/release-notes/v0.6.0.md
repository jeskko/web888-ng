JTTY decoding in the browser.

* **JTTY** (a keyboard mode: 4-GFSK, 31.25 Hz tone spacing, about 1.9 s
  per frame of a few characters, with error-correcting code and a CRC).
  The footer's **JTTY** button opens a panel:
  * it decodes the receiver's audio in the browser, in a Web Worker
    (WebAssembly);
  * it has a list of common JTTY dials to tune to;
  * messages come with their UTC time and RF frequency, and several
    signals in the passband (100-3200 Hz) are decoded at once.
  It works over HTTPS and over plain HTTP.
* The receiver (`crates/jtty`) is a Rust port of
  [jtty-cuf](https://github.com/j0uni/jtty-cuf) (MIT, its notice kept),
  made streaming:
  * jtty-cuf's receiver tests pass, and its sensitivity matches
    jtty-cuf's table;
  * it uses about 10 % of a desktop core, or about 19 % as WebAssembly.
* Decoding happens in each listener's browser, not on the Web-888: on
  the A9 it would take about four times real time. Background decoding
  on the unit (a JTTY skimmer) needs a faster receiver first.

Tested end to end in a browser over plain HTTP, against a recording with
generated JTTY signals: every message decoded, with the right RF
frequency and time. Not yet tried on live JTTY signals.

Nothing else changed since v0.5.0.
